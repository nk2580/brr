# Brr domain

A ticket is a shared local work record associated with a registered project's stable ID across its folders and worktrees. Todo, In progress, Review and Complete are its board statuses; they are separate from background Task execution states. Human and agent edits use revisions and attributed activity. A multi-folder run requires an explicit folder choice; a one-folder project supplies that folder automatically, and a project with no folders uses a private app-owned scratch workspace for reviewed runs. Missing registered folders block execution while preserving ticket editing. A reviewed execution snapshot captures project settings and the chosen folder before the host queues a linked Task. Confirmed turn attachment and successful fenced settlement may move an unchanged status automatically; later explicit status writes win. Ticket data remains available without a running inference engine. See [local ticketing](docs/adr/007-local-ticketing.md).

An interactive response is an optional native component document or isolated custom app chosen by the agent through `brr_ui_render`. Successful runtime call history and the host document hash authorize it; streamed native previews are inert. SQLite retains response-scoped interaction state separately from runtime history. A generated control can change local state or prepare an explicitly reviewed follow-up; it cannot select runtime methods, grant permissions or change collaboration mode. Task-result follow-ups enter a new foreground chat with the owning agent, preserving scheduler ownership. See [Intelligent UI](docs/adr/006-intelligent-ui.md).

A persistent agent is an optional named identity with reviewed Markdown instructions, `soul.md`, model defaults, scoped recall, learned skills and many conversations. An agent is separate from a task owner, task run, runtime thread and execution lease. Ordinary Brr chats remain available. General agent sessions need no Git folder; new repository work still uses WorkTrunk. A mention assigns a separate reviewed-context task rather than adding a second identity to an existing transcript.

SQLite is the revision authority for agents and learning. Versioned Markdown files are projections. Private agent facts and source evidence are separated by trusted session bindings; derived user/project knowledge can be shared with source provenance. All new baseline, agent and task sessions learn from newly recorded evidence. Existing historical threads are intact and are not backfilled. See [the persistent-agents decision](docs/adr/004-persistent-agents.md).

A project is a named bucket of chats with a stable app-owned ID, optional local folders, a primary folder and defaults for new chats. A chat has explicit optional project membership; its working directory never determines membership. Moving a chat changes only its bucket. Deleting a project ungroups its chats into Recents and retains hidden historical scope records; Archive all chats is a separate reviewed action that selects current membership.

A session workspace is the chat's saved execution snapshot: starting directory, all resolved roots, source-folder mappings and Git worktrees. New sessions use one WorkTrunk worktree per distinct Git repository, direct paths for non-Git folders, or a private app-owned directory when no folder is attached. All attached folders are available together. Folder/default edits apply to new sessions only; moves do not rewrite execution, task or learning scope. Resuming validates the saved snapshot and never falls back to source checkouts when metadata or roots are missing. Project IDs are distinct from filesystem paths throughout task/ticket and agent APIs. Existing-data conversion and migration are outside this development change.

A conversation is a persistent runtime thread. A turn is one user instruction and the agent's resulting work. Items are streamed messages, tool calls, command output, file changes and agent activity within a turn. An approval must be answered with its original request ID. Read-only access permits inspection; workspace-write permits edits to the saved workspace roots while retaining runtime sandbox and elevation approvals. WorkTrunk configuration and exact approved lifecycle hooks govern Git workspace creation. See [project chat buckets](docs/adr/008-project-chat-buckets.md).

The desktop host is a constrained Tauri bridge. The owned Brr runtime is a source fork of Codex CLI; it owns inference, tools, OAuth and history. Inference is authorized only by a managed ChatGPT login and the built-in OpenAI provider. API keys, externally supplied tokens and custom inference providers are excluded.

WorkTrunk is a pinned source submodule compiled into the desktop host as a native library. Setup inspection and explicit approval are local host operations. The app displays exact project hook templates, records only the approved templates and preserves the instruction for a later send. No installed WorkTrunk executable is required. Fresh Git identity reads support the long-running host without trusting stale CLI process caches.

A collaboration mode determines how the runtime works with the user. Default mode can implement a task; Plan mode explores, asks clarifying questions and produces a proposed plan using the runtime's built-in instructions. Plan mode is separate from the progress checklist and from workspace permissions. A proposed plan is ready for implementation only after its authoritative final Plan item arrives. The user can continue planning or explicitly start implementation in the same conversation. Steering adds instructions to the active turn and retains its mode.

A question request asks for explicit user input and is separate from an execution approval. Human-facing chats, agent sessions, interviews and task runs can wait through `request_user_input` or continue independent work through `request_user_input_async`, in either collaboration mode. SQLite retains the source thread/turn/item, drafts, resolution and answer-delivery intent. Background runs yield capacity in `waiting_input` without losing workspace ownership and cannot complete with unresolved questions. Replies use the original live request or a correlated continuation in the same conversation. A cancelled request is not proof of accepted input; uncertain deliveries require evidence rather than automatic replay. Temporary subagents ask through their parent and learning workers do not ask users questions. See [user questions](projects/desktop-agent/questions.md).
