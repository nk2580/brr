# Plugin and MCP host integration

Brr uses the owned Codex fork's plugin package parser, installer, cache, skill loader, hook loader, connector mappings, MCP client, OAuth store and policies. The desktop does not maintain a second plugin format or resolve an installed Codex executable.

The desktop exposes the upstream marketplace and plugin APIs, including remote search and local/Git/npm package sources declared by marketplaces. Root Agent Plugins manifests and `.codex-plugin/plugin.json` compatibility manifests remain the runtime's responsibility. Availability, administrator policy, plan eligibility, connector authorization and source failures are displayed as returned by the runtime.

MCP connections retain their complete Codex configuration objects. The desktop masks stored credentials while editing, persists reviewed changes into Brr's own engine configuration, and requests a runtime reload. MCP service credentials are separate from the ChatGPT-only inference constraint. Extension configuration writes cannot change model providers, inference credentials, sandbox policy, or arbitrary configuration files.

The runtime enables plugins, MCP 2026-07-28 for ordinary and hosted connections, local stdio protocol discovery, and tool-list change handling. Modern local servers can be discovered without a proprietary environment marker; compatible legacy servers retain the existing fallback. The owned fork adds prompt listing, prompt retrieval and completion APIs rather than a general unrestricted JSON-RPC forwarding endpoint. Prompt retrieval uses the existing MCP continuation, cancellation, OAuth and lease machinery.

App-server prompt operations run independently of its input loop so the desktop can answer an elicitation while the original request is pending. The bridge lets runtime-owned long operations finish under their configured timeout rather than dropping them at a generic transport deadline.

MCP elicitations are global pending requests, independent of the selected conversation. The desktop preserves request IDs and offers accept, decline and cancel; it validates form responses with a CSP-compatible JSON Schema interpreter and opens reviewed URLs through a constrained native browser command. Hook trust records the exact reviewed definition hash and reloads user configuration. Retrieved prompts are shown for review and only enter the user composer after an explicit action.

Portable plugin authentication retains explicit no-auth, OAuth, mixed public/OAuth and API-key declarations. API keys and provided OAuth client secrets or asymmetric signing keys are written through a constrained runtime API into the system credential store. Their identity includes the installed package root, server, endpoint and authentication declaration. Plugin responses expose credential presence and sanitized setup metadata; key material does not enter plugin files or configuration. OAuth supports public, Basic, Post and provider-registered private-key JWT clients, dynamic registration and an explicitly configured host-owned client metadata document. Endpoint, resource, scope and OpenID discovery overrides are retained. Credential-bearing endpoints require HTTPS, with HTTP allowed for loopback development servers. OpenID discovery is metadata support; this does not introduce a separate ID-token identity verifier.

MCP Apps use the official AppBridge SDK and the HTML resource profile. Each widget receives an isolated loopback origin, an outer proxy and an inner sandbox, exact origin message checks and resource-declared CSP. Tool access is limited to the originating server and declared app-visible tools, with an explicit per-call decision. Links and message insertion require a user action. Native APIs, top navigation and device permissions are not granted to widget documents.

Protocol conformance and optional feature support are distinct. Brr must not advertise unsupported capabilities or describe a working connection or installer as proof of every optional MCP extension. Tasks, Skills-over-MCP, deprecated sampling/roots, legacy HTTP+SSE transport and OpenAI native device verification remain outside the implemented profile. Brr does not impersonate a trusted upstream client or fabricate verification proofs. Hosted plugins remain subject to the user's account access; a provider may require a registered Brr client or a host-owned metadata document. These restrictions prevent an unconditional claim that every Codex plugin can run in Brr.

Sources: [OpenAI plugin packaging](https://developers.openai.com/plugins/build/plugins), [MCP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28), and the pinned source recorded in `runtime/UPSTREAM.md`.
